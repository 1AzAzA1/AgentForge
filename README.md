# Agent Forge

Десктопное приложение для оркестрации нескольких ИИ-агентов, работающих над
общей задачей под контролем ИИ-супервайзера. Все данные - профили, ключи,
переписка, отчёты - хранятся **локально** на вашем устройстве.

Возможности: локальная авторизация, воркспейсы, API-ключи, агенты,
постановка задачи и разбиение на подзадачи, ИИ-супервайзер, дашборд,
human-in-the-loop, экспорт результата и бюджеты с алертами.

Раньше проект назывался AI Orchestrator, старые профили подхватываются
автоматически.

## Версия 1.1

- Интерфейс переписан на Qt Quick: тёмная тема, переходы между экранами,
  уведомления внутри окна, палитра команд (`Ctrl+K`). Анимации можно
  ослабить или выключить в настройках.
- Ответ модели выводится на экран «Выполнение» по мере генерации, вместе с
  вызовами инструментов. Там же граф подзадач и лента событий.
- Расходы супервайзера и планировщика тоже учитываются в лимитах.
- Лок агента берётся раньше слота параллельности, пока агент ждёт ответа
  человека, слот свободен.
- Непроверенный результат не уходит в зависимые подзадачи.
- При исчерпании лимита и включённом HITL система спрашивает, поднять ли
  лимит.
- Смена пароля перешифровывает ключи в одной транзакции.
- По таймауту песочница завершает всё дерево процессов (на Windows) или
  останавливает контейнер Docker.

## Установка

**Быстрый способ.** Windows - двойной щелчок по `run.bat`. Linux и macOS:

```bash
./run.sh
```

Скрипт создаст виртуальное окружение, поставит зависимости и запустит
приложение. Первый запуск занимает 2-5 минут.

**Вручную:**

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python main.py
```

Нужен **Python 3.11+**. Подробная пошаговая инструкция со всеми
особенностями по операционным системам, настройкой бесплатного варианта на
локальных моделях и разбором типичных проблем - в файле
**[УСТАНОВКА.md](УСТАНОВКА.md)**.

**Проверка работоспособности** (без сети и без затрат на токены):

```bash
pip install -r requirements-dev.txt   # pytest, один раз
python -m pytest                # ядро, исправления и интерфейс целиком
python tests/smoke.py           # ядро, 37 сценарных проверок
python tests/ui_tour.py shots   # проход по всем экранам со скриншотами
```

Тесты интерфейса рисуют окно без экрана (`QT_QPA_PLATFORM=offscreen`) и
прогоняют задачу фейковыми агентами со стримингом: токены не тратятся.

> **Важно про пароль.** Пароль профиля одновременно служит мастер-ключом
> для шифрования API-ключей. Восстановить его невозможно: механизма
> «забыли пароль» нет и быть не может, иначе шифрование теряло бы смысл.

### Где лежат данные

| ОС | Каталог |
|---|---|
| Windows | `%APPDATA%\agent-forge` |
| macOS | `~/Library/Application Support/agent-forge` |
| Linux | `~/.local/share/agent-forge` |

Переопределяется переменной окружения `AGENTFORGE_HOME`. Внутри: `app.db`
(SQLite), `logs/`, `workspaces/` (рабочие файлы агентов), `exports/`.

## Принятые архитектурные решения

**GUI - PySide6 + Qt Quick (QML).** Нативное окно на Windows/macOS/Linux без
веб-прослойки и без Node.js. Qt Quick рисует интерфейс на GPU, поэтому живой
фон, переходы и графики не тормозят даже во время прогона. Интерфейс лежит в
`ui/qml`, данные ему отдаёт мост `ui/bridge`: контроллер на каждый экран и
модели списков, которые сообщают QML только о реальных изменениях, поэтому
списки анимируют добавление и удаление карточек. Шрифты (Inter, JetBrains
Mono) и иконки (Lucide) идут в комплекте, от системы ничего не требуется.

**Параллелизм - один asyncio-луп.** Qt и asyncio объединены `qasync`, агенты -
обычные таски в этом лупе. 15+ агентов не превращаются в 15 потоков. Блокирующие
операции (SQLite, `ddgs`) уводятся в `asyncio.to_thread`, исполнение кода - в
отдельный процесс или контейнер.

**Шифрование ключей.** `Argon2id(пароль профиля, соль)` -> 32-байтовый мастер-ключ,
живёт только в оперативной памяти. API-ключи шифруются `AES-256-GCM`. БД остаётся
обычным SQLite, но секреты в ней нечитаемы. Смена пароля автоматически
перешифровывает все ключи. Опция «запомнить пароль» использует хранилище
секретов ОС (`keyring`).

**Песочница - интерфейс с двумя реализациями.** `DockerSandbox`
(`--network none`, `--read-only`, лимиты памяти/CPU/PID, `--cap-drop ALL`)
используется, если Docker доступен. Иначе `SubprocessSandbox`: одноразовый
каталог, своя группа процессов, `RLIMIT_CPU/AS/FSIZE/NPROC`, вычищенное
окружение без ключей хоста, сеть отрезана подстановкой недоступного прокси.
Второй режим - барьер по умолчанию, а не полная изоляция, и приложение говорит
об этом прямо в настройках.

**Права на файлы.** Агент работает в каталоге своего воркспейса. Пользователь
может добавить дополнительные каталоги в настройках - проверка пути
централизована в `ToolContext.resolve` и отсекает `../`, абсолютные пути и
симлинки наружу.

**Изоляция агентов.** История каждого агента лежит в таблице `messages` и
всегда выбирается с фильтром по `agent_id`. Кросс-агентных выборок в коде нет,
поэтому один агент физически не может увидеть контекст другого. Единственный
канал обмена - анонимизированная сводка супервайзера.

**Стоимость.** Провайдеры почти никогда не возвращают цену, только токены.
Поэтому расход считается на клиенте по таблице `providers/pricing.json`
(USD за 1 млн токенов, поиск по точному совпадению и по префиксу). Локальные
модели стоят 0. Таблицу можно править вручную под актуальные прайсы.

## Как устроено выполнение

Вкладка **«Выполнение»** запускает прогон: оркестратор строит волны подзадач,
у которых выполнены зависимости, и гонит их параллельно (по умолчанию до 6
одновременно). Один агент не берёт две подзадачи сразу - на него стоит
персональный лок, поэтому его личная история остаётся связной.

Каждый агент работает в цикле ReAct: модель думает -> вызывает инструменты ->
получает результат -> продолжает. Остановка наступает по одному из условий:
агент выдал блок `RESULT:`, кончились разрешённые шаги, исчерпан лимит токенов
задачи, пользователь нажал «Остановить».

Из ответа разбираются две вещи: блок `RESULT:` становится результатом подзадачи,
а строка `CONFIDENCE: 0..1` - самооценкой, по которой срабатывает пауза
human-in-the-loop. Готовый результат сохраняется в `reports` - их и
проверяет супервайзер.

Расход токенов пишется в `usage_log` после каждого вызова модели, поэтому
стоимость видна в реальном времени и лимит задачи срабатывает до, а не после
лишнего запроса.

Пауза и остановка работают корректно: пауза держит агентов на `asyncio.Event`
перед началом следующей подзадачи, остановка отменяет задачи и закрывает
HTTP-клиенты.

## Как работает супервайзер

**Чем он думает.** В настройках воркспейса выбирается одно из двух: агент с
вашим API-ключом или локальная модель через Ollama (по умолчанию Qwen). Второй
вариант работает офлайн и ничего не стоит - разумно, когда проверок много.
Температура у супервайзера жёстко занижена: проверка требует предсказуемости,
а не фантазии.

**Чек-лист.** Каждый отчёт проверяется по четырём пунктам: соответствие
заданию, логическая непротиворечивость, фактические ошибки и выдуманные
источники, согласованность с ранее принятыми результатами проекта. Вердикт
приходит структурированным JSON: `ok`, `rework` или `conflict` плюс список
замечаний с уровнем важности.

Нечитаемый ответ супервайзера трактуется как «нужна доработка», а не как
«принято»: молча пропустить непроверенный отчёт хуже, чем перепроверить.
Если супервайзер вовсе недоступен или упёрся в лимит, результат считается
**непроверенным**: с включённым human-in-the-loop система спрашивает вас,
без него результат остаётся «на проверке» и не уходит в зависимые подзадачи.
Строить дальше на непроверенном значит размножить возможную ошибку.

**Доработка.** Вердикт `rework` возвращает подзадачу тому же исполнителю
с замечаниями - до `max_rework_rounds` раз (по умолчанию 2). Лок агента
держится всё это время, поэтому его личная история остаётся связной.
Когда доработанный результат принимают, замечания, из-за которых он уходил
на второй круг, закрываются автоматически.

**Анонимные сводки.** Супервайзер видит отчёты как «Исполнитель A/B/C» и
пересказывает их своими словами в трёх разделах: факты, расхождения, открытые
вопросы. Перед сохранением текст дополнительно вычищается от имён агентов -
на случай, если модель всё-таки кого-то назвала. Сводка ложится в таблицу
`summaries`, и каждый агент подхватывает свежую при следующем запуске, не зная,
кто из коллег что написал. Рассылка идёт и по таймеру (раз в N минут), и по
событию (завершена подзадача), и вручную кнопкой на экране «Супервайзер».

**Конфликты.** В конце прогона результаты сравниваются между собой. Если
расхождение имеет объективный разрешающий признак - свежая дата, первичный
источник, арифметическая проверка - инцидент закрывается автоматически с
объяснением. Если нет, он эскалируется пользователю и ждёт решения на экране
«Супервайзер».

## Дашборд

Шесть счётчиков сверху: агенты, готовые подзадачи, израсходованные токены
(с долей от лимита задачи, если он задан), примерная стоимость, число
доработок и число инцидентов, ждущих решения. Последние два подсвечиваются
цветом, только когда они ненулевые - иначе это просто шум.

Полоса прогресса разбита на цветные сегменты по статусам подзадач, поэтому
видно не только «сколько готово», но и сколько висит на доработке или упало
с ошибкой.

Графики нарисованы средствами Qt Quick (Canvas и Shapes), без QtCharts:
расход нарастающим итогом (деньги и токены, с подсказкой при наведении) и
расход в разрезе агентов, где отдельно видна доля проверок супервайзера.

Ниже - список агентов с текущим статусом и тем, над чем каждый работает
прямо сейчас, объединённая лента отчётов и сводок (с вердиктом супервайзера
и самооценкой уверенности) и колонка инцидентов.

Обновление идёт по шине событий, но с троттлингом: во время прогона события
летят пачками, и перерисовывать всё на каждое бессмысленно. Таймер собирает
их в один апдейт не чаще раза в секунду, а мелкие события вроде «шаг 3/10»
дашборд игнорирует - им место в ленте выполнения.

**Что стоит посмотреть в первую очередь.** На тестовом прогоне из трёх
подзадач супервайзер израсходовал 68% всех токенов: он читает каждый отчёт
и составляет сводку после каждого события. Если счёт растёт быстрее
ожидаемого, начните с графика «Расход по агентам» - чаще всего дело не
в исполнителях, а в частоте сводок. Она настраивается на экране
«Настройки», а для проверок можно поставить локальную модель через Ollama.

## Human-in-the-loop

Режим включается переключателем в настройках воркспейса. Когда он включён, система
действительно **останавливается и ждёт**, а не просто помечает проблему
задним числом.

**Точки остановки.** Супервайзер нашёл конфликт или не принял результат
после доработок. Супервайзер не смог проверить результат. Исполнитель сам
оценил свою уверенность ниже порога (настраивается, по умолчанию 0.5; ноль
отключает этот триггер). Исчерпан лимит бюджета: можно поднять его на 50% и
продолжить. Завершён этап работ - опциональная пауза перед следующей волной.

**Решения.** Принять результат как есть. Вернуть исполнителю -
ваш комментарий уходит ему первым, раньше замечаний супервайзера. Пропустить
подзадачу, пометив её неудачной. Остановить весь прогон.

**Почему панель, а не модальное окно.** Вопросов может быть несколько
одновременно, если параллельно работают разные агенты. Модалка заслоняла бы
прогресс и ленту - то есть ровно то, по чему принимается решение. Поэтому
карточки встроены в страницу «Выполнение», прямо под полосой прогресса.

К каждому вопросу прилагается выжимка: текст подзадачи, замечания
супервайзера и результат исполнителя. Решать вслепую не приходится.

**Про лимиты доработок.** Настройка `max_rework_rounds` ограничивает
автоматические доработки супервайзера. Когда доработку назначаете вы,
выдаётся дополнительный круг сверх этого лимита - ваше решение важнее
настройки. Всего человек может выдать до трёх дополнительных кругов:
без этого потолка цикл «вернул - переделал - вернул» не заканчивался бы.

Вся история вопросов и ответов пишется в таблицу `approvals` и видна на
экране «Супервайзер» -> «Решения».

## Экспорт результата

**Один сборщик, четыре формата.** Из базы и рабочего каталога собирается
модель документа - список блоков, - и уже её рендерят Markdown, DOCX и PDF.
Содержание у трёх форматов совпадает по построению: правится один сборщик,
а не три экспортёра.

**Автоопределение с объяснением.** Формат подбирается по тому, что реально
наработано, и по формулировке задачи: нашлись файлы с кодом - предлагается
ZIP со структурой каталогов; задача звучит как «подготовить отчёт» -
предлагается DOCX; результат короткий и текстовый - Markdown. Рядом с
предложением всегда написано, **почему** выбран именно этот формат, поэтому
переопределить его можно осознанно. Явно заданный при постановке задачи
формат всегда побеждает автоопределение.

**Что включать - решаете вы.** По умолчанию в документ идут результаты
подзадач, инциденты и статистика прогона. Отдельными переключателями добавляются
полные отчёты исполнителей, сводки супервайзера и ваши решения. Есть режим
анонимизации: имена агентов заменяются на «Исполнитель A», «Исполнитель B» -
удобно, когда документ уходит наружу.

**Кириллица в PDF.** Встроенные шрифты PDF её не знают, поэтому приложение
ищет TrueType-шрифт в системе (DejaVu, Liberation, Arial), а если системных
нет - берёт DejaVu из пакета matplotlib. Когда шрифт не найден вообще,
экспорт не выдаёт кракозябры молча: он объясняет проблему и предлагает
DOCX или Markdown.

**ZIP** содержит `RESULT.md`, каталог `files/` с сохранённой структурой и
`manifest.json` с машиночитаемым описанием подзадач, инцидентов и расхода.
Служебные каталоги вроде `.sandbox`, `__pycache__` и `node_modules` в архив
не попадают.

## Бюджеты и лимиты

**Три уровня.** Лимит ставится на весь проект, на текущую задачу и на
отдельного агента. Каждый уровень ограничивается и по токенам, и по деньгам.
Пустое поле означает «без ограничения» - так же, как лимит токенов при
постановке задачи.

**Проверка до вызова, а не после.** Перед каждым обращением к модели
проверяются все три уровня, от общего к частному. Узнавать о превышении
постфактум бессмысленно: деньги уже потрачены. Проверки супервайзера и
планирование проходят через тот же бюджет. Когда лимит упёрся, при включённом
human-in-the-loop система спрашивает, поднять ли его; параллельные агенты
ждут одного общего ответа. Без human-in-the-loop подзадача получает статус
ошибки с внятным текстом - например, «агент «Аналитик»: израсходовано
600 токенов из 500».

**Расход берётся из журнала вызовов.** Источник правды - таблица
`usage_log`, а не накопительные счётчики. Поэтому перезапуск приложения не
обнуляет израсходованный бюджет сам собой.

**Алерт срабатывает один раз на уровень.** Порог настраивается (по умолчанию
80%). Повторять предупреждение на каждом вызове значило бы превратить его
в шум, который перестают замечать.

Суммы форматируются с адаптивной точностью: лимит в четыре десятитысячных
доллара - обычная величина на дешёвых моделях, и округление до центов
превратило бы сообщение в бессмысленное «$0.00».

## Известные ограничения

* Графики на дашборде показывают всю историю воркспейса без фильтра по
  отдельным прогонам.
* Планировщик пока не расставляет зависимости между подзадачами сам:
  их задают в редакторе подзадачи на экране «Задача».
* Следующая волна подзадач стартует после завершения всей текущей волны.
* В режиме `subprocess` песочница ограничивает ресурсы и окружение, но не
  изолирует файловую систему полностью. Для строгой изоляции установите Docker
  и выберите его в настройках воркспейса.
* Цены в `pricing.json` ориентировочные - сверяйтесь с прайс-листами провайдеров.
